# M11 — as-of evaluation: feasibility and proposed contract

**Status: design only.** Nothing was ingested, fitted or docked for this
document. It uses public metadata and the data already on disk. No experiment
contract here is frozen yet; §7 argues that one of the things being proposed
*cannot* be made confirmatory by any amount of care applied to data we have
already read.

M10 is closed as a bounded historical docking experiment: the FAIL decision, its
recorded metrics, the uncertainty qualification and the unresolved

- "BindingDB cuts a new archival version, which includes detailed metadata, on a

- each archival release carries a **DOI**.

### Licensing — and a discrepancy to resolve

Our `source_release` rows record `CC-BY-3.0 (BindingDB-curated); CC-BY-SA-3.0
(ChEMBL-derived rows)`. **Resolved in M11b**: every archival deposit declares
**CC BY 4.0** in its DataCite rights metadata, matching the 2024 paper, so our
recorded string is **stale** for the BindingDB-curated portion. The
ChEMBL-derived CC BY-SA 3.0 carve-out is described in the literature but is *not*
broken out in the deposit rights metadata, so it remains unverified at deposit
level. The share-alike term on ChEMBL-derived rows constrains
redistribution of any derived benchmark, so this must be checked against the
specific archival deposit's own metadata before anything is republished — not
inherited from what we wrote down in M2.

## 2. Does a snapshot represent what was available at its date?

**Partly, and the gap matters.** Three distinct dates exist and none of them is
"when this record became retrievable":

| Field | What it is | Coverage in our 202609 |
| --- | --- | --- |
| `publication_date` | the article's date | 2.74% unparseable (`//0` and similar) |
| `bindingdb_date` ("Date in BindingDB") | when the record entered BindingDB | **0% unparseable** |
| snapshot date | when the file was cut | exact, from the release label |

Both date fields are stored as **raw `M/D/YYYY` text**, not dates. `max()` over
them is string ordering, not chronology — a trap this project already stepped in
once while writing this document. Any as-of logic must parse first and record a
per-row parse outcome.

A snapshot is a faithful record of **what the file contained when cut**. It is
*not* a reconstruction of the database's state at an arbitrary earlier date,
because BindingDB revises and back-fills: a record present in a 2026 snapshot
with `bindingdb_date` in 2019 may have been corrected after 2019, and the
snapshot shows the corrected form. So:

- **`bindingdb_date` ≤ T within one snapshot** is a *proxy* for availability at T,
  with back-fill and revision unaccounted for. This is exactly what
  `temporal_proxy-v4` already is, and why it is labelled a proxy.
- **Snapshot A versus snapshot B**, A cut before B, is a *true* as-of comparison
  for the increment: a row in B and not in A genuinely was not in the file at A's
  date. This is the only construction that earns the name.

The second requires two snapshots. We hold one.

## 3. Matching entities across releases without surrogate IDs

`BindingDB Reactant_set_id` is a database surrogate. In our corpus
`(reactant_set_id, measurement_type, relation, value_text)` is perfectly unique
across all 3,233,963 activities — which is precisely why it is seductive and why
it must not be the key: nothing guarantees it is stable across releases, and if
it is reassigned the match fails silently in the direction of inventing new
pairs.

Identity rests on content, with **normalised external** provenance
disambiguating. Our `publication.id` is a local surrogate assigned at ingest and
is meaningless across releases, so it must not appear in any cross-release key.

| Level | Key | Already stored |
| --- | --- | --- |
| Compound | **InChIKey** of the RDKit-standardised parent | `compound.inchikey` |
| Target | **SHA-256** of the uppercased, whitespace-stripped sequence | `target.sequence_sha256` |
| Publication | **normalised PMID, else normalised DOI, else normalised patent number** | `publication.pmid`, `.doi`, `.patent_number` |
| Assay context | pH and temperature as normalised text | `activity.ph_text`, `.temp_c_text` |

### 3.1 Two different keys, because they answer different questions

The previous draft used a single fingerprint containing value, relation and type,
and then defined a correction as "the same key with a different value". That is
incoherent: a fingerprint containing those fields **cannot** stay fixed when they
change. Matching therefore uses two nested keys.

**The observation slot** — what a measurement is *about*, with no outcome in it:

```
slot = (compound.inchikey,
        target.sequence_sha256,
        normalised_publication_ref,     # PMID | DOI | patent, in that order
        normalised_ph, normalised_temp,
        curation_source)
```

**The observation value** — what was reported:

```
value = (measurement_type, relation, value_text_normalised)
```

A measurement is `(slot, value)`. The slot is stable under correction; the value
is exactly what a correction changes. Nothing else in the design depends on a key
that must be simultaneously stable and sensitive.

### 3.2 Deterministic multiset matching

Within a snapshot, a slot may legitimately carry several rows. Matching is
therefore over **multisets with counts**, and the procedure is fixed so that two
runs over the same inputs give identical output:

1. normalise every field by a declared rule (case, whitespace, unit, numeric
   formatting), recording the normalisation version;
2. group rows by `slot`, then by `value`, in a **sorted canonical order** —
   sorted by the serialised slot, then the serialised value, then by a stable
   row digest — so the pairing of equal-valued rows never depends on file order
   or database return order;
3. for each `(slot, value)`, compare the count in A with the count in B;
4. pair rows positionally within the sorted order; surplus on either side is
   carried to step 5.

| Comparison | Classification |
| --- | --- |
| count equal, > 0 | **unchanged** |
| count in B > count in A | **addition** at that slot |
| count in B < count in A | **removal** at that slot |
| slot absent from A | **new slot** |
| slot absent from B | **removed slot** |

### 3.3 Corrections are inferred, not matched

A correction is a *hypothesis* linking a removal to an addition at the **same
slot**. It is only asserted when provenance supports the link:

- same slot, and
- exactly one unmatched removal and one unmatched addition at that slot
  (a one-to-one pairing; ambiguous many-to-many sets are never linked), and
- the surrogate `reactant_set_id` is **identical** across the two rows, or some
  other release-stable row identifier is.

If those conditions hold, the pair is classified **corrected measurement**.
If they do not, the rows stay classified as an **unresolved addition** and an
**unresolved removal**, reported as such. We do not guess that a value changed
when the files only show one row gone and another arrived.

Whether `reactant_set_id` is release-stable is **unknown** (§9). Until it is
established, every correction link is provisional, and the count of unresolved
additions/removals is the headline diagnostic — a large count means the matcher
cannot distinguish correction from churn, which is a finding, not a failure.

#### 3.3a A release-stable identifier we already hold but never lifted

M11b found a better anchor than the surrogate. The source TSV carries a
**`BindingDB Entry DOI`** column — e.g. `10.7270/Q2ZW1J3M` — present in
`raw_measurement.payload` for every ingested row. It is an **externally minted,
DOI-backed identifier**; DataCite lists 57,709 such per-entry DOIs under prefix
`10.7270`.

We did **not** lift it into the curated `publication` table, which holds only
`pmid`, `doi` and `patent_number`. That is the identifier correction links should
prefer, because unlike `reactant_set_id` it is registered externally and so has a
reason to be stable across releases rather than merely appearing to be.

The matcher therefore tries `entry_doi` first and `reactant_set_id` second, and
records which one carried each link. **Lifting the column into the curated layer
is a prerequisite for M11c**, and is on the freeze checklist (§11).

### 3.4 What repeated identical rows do and do not mean

Measured on our corpus under the earlier draft's key: 3,233,963 rows reduce to
3,169,182 distinct tuples. The difference, 64,781, is **excess rows beyond the
distinct tuples — 2.00%**. An earlier draft described that figure as the share of
rows sharing a fingerprint with another row, which it is not: a group of *k*
identical rows contributes *k* such rows but only *k−1* excess.

Both quantities, computed separately:

| | Count | Share of rows |
| --- | ---: | ---: |
| excess rows beyond distinct tuples | 64,781 | **2.00%** |
| rows belonging to a repeated group | 122,170 | **3.78%** |
| repeated groups | 57,389 | — |

Recomputed under the slot/value keys above in M11b.

The previous draft called these "genuine duplicate rows (the same measurement
recorded twice)". **That is not established.** Identical tuples are consistent
with at least three situations and the files do not distinguish them:

- two genuinely independent replicate experiments reported in one article;
- one experiment ingested twice through different curation routes;
- two distinct experiments whose differing conditions are not captured by the
  fields we key on.

So repeated identical rows are treated as **indistinguishable observations at a
slot**, counted, and never asserted to be duplicate experiments. The count
difference between snapshots is what the matcher uses; the interpretation is left
open and reported.

### 3.5 Two caveats that will cost rows

- **Standardiser drift.** InChIKeys depend on our RDKit version and
  standardisation pipeline (`m3/v3+rdkit-2026.03.6/...`). Both snapshots must be
  curated with the *same* pinned curator version, or apparent "new compounds"
  will be standardisation artifacts.
- **Sequence revision.** If BindingDB updates a target sequence, its digest
  changes and the target looks new. Sequence matching must be backed by a
  UniProt-accession join as a second opinion, with disagreements reported.

## 4. Classifying the delta between two snapshots

Classification describes the **evaluation** set and the **audit** record. It does
not reach back into training; §5.2 and §5.4 define the training population from
snapshot A alone.

For each slot in the later snapshot B, relative to earlier snapshot A, with all
aggregation done **within** partition and never across:

| Class | Definition | Role |
| --- | --- | --- |
| **new pair** | `(compound, target)` has no slot in A | the prospective stratum |
| **recurrent pair** | the pair has slots in A, and B adds observations | reported separately; near-interpolation |
| **unchanged pair** | present in A, no additions in B | not in the evaluation set; still in training |
| **unresolved addition** | an extra observation at a slot, no correction link | eligible as new evidence; flagged |
| **unresolved removal** | an observation gone from a slot, no correction link | **audit only**; see below |
| **corrected measurement** | a removal and an addition linked per §3.3 | **audit only**; excluded from the evaluation set |
| **newly decisive censored** | straddled θ in A, decisive in B — **either** direction (see §5.4) | eligible, **own stratum**, direction recorded — the label exists because evidence tightened |
| **newly ambiguous** | decisive in A, ambiguous in B | excluded from the evaluation set, counted |

### 4.1 Why removals and corrections are audit-only

A measurement withdrawn or corrected in B tells us something about BindingDB's
curation, not about a model's ability to predict. It cannot be an evaluation
label, because there is no stable label to score against. And it must not change
the training set either — that is the subject of §5.4.

So each is counted, reported per class and per target, and carried in an audit
table with the slot, both values and the evidence for or against a correction
link. If removals or corrections are concentrated in particular targets or
sources, that is reportable in its own right.

### 4.2 Accrual: entry-date counts within one snapshot

**These are not measured release increments.** They are counts of rows in our
single 202609 snapshot grouped by `bindingdb_date`, the date BindingDB records
for when a row entered. They are the best available indication of accrual rate,
and they are **not** the same thing as the diff between two releases: they cannot
show withdrawals or corrections, and back-fill means a row's entry date need not
be when it first appeared in a published file.

New Ki rows by `bindingdb_date` month, 2026, within snapshot 202609:

| Month | Ki rows |
| --- | ---: |
| 2026-01 | 94 |
| 2026-02 | 175 |
| 2026-03 | 225 |
| 2026-04 | 260 |
| 2026-05 | 398 |

### 4.3 A release-level increment estimate, from deposit metadata

The inventory gives something the entry-date counts cannot: measurement totals at
**declared version dates**. Differencing those is a real release increment, not a
within-snapshot proxy.

| From | To | Elapsed | Approx. increment |
| --- | --- | --- | ---: |
| 2025-10-01 (3.08 M) | 2026-07-01 (3.22 M) | 3 quarters | ~140,000 |
| 2024-10-01 (2.9 M) | 2025-10-01 (3.08 M) | 4 quarters | ~180,000 |
| 2023-10-01 (2.6 M) | 2026-07-01 (3.22 M) | 11 quarters | ~620,000 |

These are differences between **rounded** counts quoted in prose, so they are
approximate **net growth** — additions minus withdrawals minus any re-curation
that merged or split rows — and **not** a count of added measurements. Net growth
hides withdrawals entirely: a release that added 60,000 and withdrew 10,000 looks
identical to one that added 50,000 and withdrew none.

≈ **47,000 net per quarter** across all measurement types. Projecting that onto
Ki would need our corpus's 19.2% Ki share to hold for other releases, which we
have **not measured** — so the figure of ~9,000 Ki rows per quarter is an
**unmeasured assumption**, not a result. **Back-fill is likewise unmeasured**: net
growth says nothing about how much of an increment is genuinely recent. And none
of these totals is filtered to our eligibility rules, so the usable new-pair
count remains unknown.

The two estimates disagree by roughly an order of magnitude — §4.2's entry-date
counts give ≈600 Ki rows per quarter against this section's assumed ≈9,000. **We
cannot currently say which is closer**, and the disagreement is itself the
finding: entry dates within one snapshot cannot see back-fill, while rounded
release totals cannot see withdrawals, type mix, or eligibility. Both are
approximations built on different unmeasured assumptions.

Only a **real two-snapshot diff** settles it, and until one is run §5.1's
minimum-count rule cannot be sized against either number with confidence.

**Provisional reading.** On these figures a one-month gap looks far too small to
populate a per-target ranking evaluation — hundreds of rows before eligibility
filtering, before the exact/censored split, and before requiring both classes on
the same target. But increment feasibility **remains provisional until two
snapshots are actually compared**: only a real diff gives the eligible-new-pair
count, and only a real diff shows the removal and correction rates. The gap
should be chosen on a pre-declared minimum eligible new-pair count measured from
a real diff, not from these entry-date counts.

## 5. Proposed experiment contract

Written to be frozen *before* any ingest. Not yet frozen.

### 5.1 Snapshots

| Role | Snapshot | Status |
| --- | --- | --- |
| Earlier training snapshot | an archived quarterly deposit, **identified by DOI and digest**, cut at `T_train` | **not yet identified** — blocked on §1 |
| Validation | drawn from **within** the earlier snapshot, by `bindingdb_date` below `T_train`, label-blind clustering as in M5 | specified |
| Later evaluation snapshot | an archived deposit cut at `T_eval`, with `T_eval − T_train` chosen to clear a **pre-declared minimum eligible new-pair count**, not a fixed interval | **not yet identified** |

The minimum new-pair count is declared before the snapshots are chosen, so the
gap is selected on a quantity fixed in advance rather than on which gap gives a
better-looking result.

### 5.2 Partition-specific endpoint construction

The M4 ordering error must not reappear, and neither must a subtler one: the
training population is defined by **snapshot A alone**.

1. **Training population.** Every eligible measurement **present in snapshot A**
   is training evidence — including measurements that are also present in B, which
   is nearly all of them. An earlier draft said "in A only → train", which would
   have discarded the entire overlap and left training with almost nothing. A
   measurement does not stop being historical evidence because it survives into a
   later release.
2. **Evaluation population.** Built from the **newly added observations** only,
   with the strata of §4, under the three-way separation of §5.2a. An earlier
   draft left this ambiguous and example (e) silently used a different rule.
3. Build `pair_regression` and `pair_label` **independently within each
   partition**, stamped with that `partition_scope`.
4. Assert that no aggregate spans partitions — the existing `temporal_proxy`
   assertion, reused.

Each partition gets its own `endpoint_version` row, as `temporal_proxy-v4`
already does. An aggregate computed over the union is a different object and is
not admissible.

#### 5.2a0 Three representations, held separately

Each reading needs its own evidence, and deriving one from another has twice
produced a wrong answer:

| Representation | What it is | Read by |
| --- | --- | --- |
| `in_a` | historical A evidence | training |
| `in_b` | **complete** actual B evidence, corrections included | full-B audit, consistency screen |
| `increment` | **eligible** new evidence, corrections withheld | increment label |

Two failures this fixes, both found by reproducing them:

* **A publication move cancelled itself.** Deriving the increment as a multiset
  difference of `Measurement` compares relation and value only. With A holding
  exact Ki 10 nM at publication 1 and B the same value at publication 2, the
  matcher reported one addition and one removal at two different slots, and the
  value-level subtraction cancelled them — the harness saw an empty increment.
  The increment is now assembled from the matcher's **counted addition rows**,
  which carry their slots.
* **A withheld correction vanished from B.** Withholding a correction candidate
  from `in_b` kept it out of the increment *and* out of actual B, so the full-B
  audit read `no_usable_evidence` for a pair B plainly had evidence for.
  Withholding now applies to the increment alone.

Withholding selects **counted occurrences**, not every row sharing a (slot,
value) key, so an unchanged observation that happens to share a correction's
after-value survives.

#### 5.2a Three things that were being conflated

"What B says about a pair" can mean three different things. The previous draft
used one in §5.2 and another in example (e), which is the inconsistency being
fixed here. They are now named and separated, and only one of them forms labels.

| | What it is | Role |
| --- | --- | --- |
| **(i) increment label** | the endpoint label computed from the **newly added observations alone**, under partition-scoped aggregation | **forms the evaluation label.** This is the as-of quantity: the evidence that arrived. |
| **(ii) full-B status** | the endpoint status computed over **snapshot B's actual evidence** | **audit only by default.** Recorded for every evaluation pair whichever branch it falls in. |
| **(iii) consistency screen** | an eligibility filter that *uses* (ii) — drop pairs whose full-B status is contradictory | **a declared filter**, reported both ways (§5.2b). It is not a label and never changes one. |

Each reading draws on **exactly one** source, and the code enforces that by
holding A and B separately rather than reconstructing one from the other:

| Reading | Source |
| --- | --- |
| training | `in_a` alone, always |
| increment label | `added` — the multiset difference B − A |
| screen | `in_b` alone, B as it actually stands |

**Actual B, not A plus additions.** An earlier draft computed the full-B status as
the union of A's evidence and B's additions. That is only equal to B while B
never removes anything. When B *withdraws* one of A's observations, the union puts
the withdrawn row back and the screen then rejects a pair on evidence that no
longer exists — see worked example (g), where a withdrawn inactive bound turned a
perfectly clean active pair into a manufactured contradiction.

**Declared primary protocol.** Labels come from (i). The primary result applies
the (iii) screen. Both the screened and unscreened numbers are reported, so the
contribution of contradictory pairs is visible rather than buried in a choice.

Why the screen is defensible and why it still has to be declared: a pair whose
increment contradicts A is not a clean test of ranking — scoring the model for
failing to predict a value that disagrees with its own training evidence measures
measurement heterogeneity, not generalisation. But the screen reads B beyond the
increment, so it is pre-registered, labelled, and reported with and without.
Choosing between them after seeing the two numbers is exactly what this
separation exists to prevent.

#### 5.2b What each choice may and may not touch

| | Primary (screened) | Sensitivity (unscreened) |
| --- | --- | --- |
| Label source | (i) increment | (i) increment |
| Pairs dropped | full-B `exact_bound_conflict` or `empty_intersection` | none on consistency grounds |
| Training population | **identical** | **identical** |

**Training is invariant across every evaluation choice above.** No screen, no
stratum definition and no label rule reaches partition 1. That is asserted, not
assumed: the training population is rebuilt from A alone and compared by digest
under each evaluation variant.

**Nothing read from B may change partition 1.** The training set is exactly what
an analyst standing at `T_train` with snapshot A in hand would have had. That is
the whole content of the as-of claim, and it is checkable: the training
population must be reproducible from A's digest alone, without B present.

### 5.3 Train-only transforms and activity-derived features

Label-blind, so computable on both partitions: ECFP4 fingerprints (from SMILES),
ESM-2 embeddings (from sequence), sequence and chemistry clustering, length and
heavy-atom policies.

**Activity-derived, therefore train-partition only**, and each already has
split-scoped machinery that must be used:

| Artifact | Why it leaks if pooled |
| --- | --- |
| `activity-target-*` feature caches | derived from measurements; `feature_version.split_id` exists for exactly this and must be set |
| B0 per-target mean | a test label leaks into its own prediction |
| B3 kNN retrieval index | the index must contain no evaluation-partition `activity_id` |
| Evidence payloads | `evidence_mode = evaluation` restricts to the train partition; asserted |
| Near-homolog / `split_target_stratum` | computed from the partition structure, recomputed per split |
| Candidate library membership | frozen and label-blind, but must be re-checked against the later snapshot |

Every one of these is an existing build-failing assertion in M5/M7, not new work.

### 5.3a Validation is reserved inside A, and is not training evidence

Validation must come from **within snapshot A** — using any part of the B
increment to select a model would make the as-of evaluation a test of something
already optimised against. So A is cut into `train` and `validation` by
`bindingdb_date`, label-blind, with the M5 clustering applied so the split is not
merely random.

**Under `train_only`, validation evidence must not reach anything fitted or
retrieved.** Reserving rows for validation is not enough; the leak would be
indirect. Concretely, the validation partition's measurements must not enter:

| Artifact | Why it would leak |
| --- | --- |
| `activity-target-*` feature caches | an activity-derived feature carrying validation evidence hands the model its own validation labels; `feature_version.split_id` must scope to `train` |
| B0 per-target means | a validation label leaks into its own prediction |
| B3 kNN retrieval index | the index must contain no validation-partition `activity_id` |
| Evidence payloads | `evidence_mode = evaluation` must restrict to `train`, not to A |
| Near-homolog strata | recomputed from the train partition only |

`seq2lead.asof.evaluation` provides the gate — `select_for_fitting` and
`assert_no_reserved_evidence`, with `FITTABLE_PARTITIONS = {"train"}` — and it is
tested for all five artifacts.

**That is not the same as the gate being enforced.** The production builders in
`features/`, `eval/baselines.py`, `retrieval/` and `evidence/` do **not** call it,
and their existing assertions are written `train` versus `test`, which would let
validation evidence through. Integration therefore remains **open** on the freeze
checklist, and will stay open until each production artifact builder calls the
gate. A gate that exists and is not wired in protects nothing.

`temporal_proxy-v4` already carries `protocol: train_only` with
partition-specific endpoints, and that remains unchanged — M11 adds a partition,
it does not relax the existing one.

#### 5.3b What is wired, and what only looks wired

Three of the five artifacts of §5.3a have a production path that the as-of
experiment will actually call, and they are verified against a live three-way
partition. Two do not, and saying so is the point of this subsection.

| Artifact | Production path | Status |
| --- | --- | --- |
| Activity-derived features | `features.activity.build_entity_activity_features`, which embeds the SQL gate | **verified** — each partition is given a distinct pKi, so a leak moves the mean rather than only a count |
| Baseline target statistics | `eval.cohort.build_cohort` → `GlobalAndTargetMean.fit` | **verified** through the real loader, with partition-specific endpoints |
| The gate itself | `splits.assertions.training_visible_activities` | **verified** — returns exactly `train`, and the harness gate selects the identical set |
| Retrieval index | *none* | **unimplemented** — the guard exists and is tested; nothing calls it |
| Evaluation-mode evidence | *none that filters* | **unimplemented** — see below |

**On evidence, correcting an earlier claim.** A previous report said
evaluation-mode evidence was verified as restricted to the train partition. It is
not. `rank._prior_evidence` queries `activity` with no partition predicate, and
its own docstring says "demo only". What the CLI enforces is that evaluation mode
passes `show_evidence=False`, so **no** evidence is displayed — which is safe,
but it is suppression rather than filtering. An as-of run therefore runs with
evidence off, and that is a limitation to report, not a safeguard to claim.

### 5.4 Eligibility, conflicts, censoring, recurrence

**Eligibility** is evaluated **within a partition, from that partition's snapshot
only**: `status = 'ok'`, `in_benchmark_scope'`, not `excluded_from_eval`, label in
{active, inactive} — the `ki-pki6-v2` rules, applied to A for training and to the
B increment for evaluation.

**Conflicts, and the future-leakage trap.** A pair whose exact aggregate falls
outside its censored interval is `exact_bound_conflict` and excluded — but
*the determination is made within each partition separately*:

- a pair that is **clean in A** is training evidence, and **stays** training
  evidence even if evidence added in B makes it contradictory. Removing it would
  mean the historical training set depended on the future, which is exactly the
  leakage an as-of design exists to prevent. An earlier draft said "a pair whose
  status changes between snapshots is excluded and counted", which had precisely
  this defect.
- that pair is, however, **excluded from the evaluation set**, because B gives it
  no stable label to score.
- the transition is recorded in the **audit table**: clean in A, contradictory in
  B, with both evidence sets. A model trained on evidence later shown to be
  contradictory is a real and reportable limitation — it is reported, not
  retroactively repaired.

The same rule governs corrections and withdrawals: **no observation is removed
from the training population because of anything discovered in B.** Their
treatment is evaluation exclusion plus an audit entry, never a change to history.

**Censoring — both branches.** A decisive bound can establish **either** class.
An earlier draft said decisive censored records "are negatives", which is wrong:
a tight upper bound on Ki is a *lower* bound on pKi and can decide **active**.
Matching `seq2lead.endpoint.interval` as implemented, with θ the activity
threshold:

| Evidence | Implied pKi constraint | Decisive when | Label |
| --- | --- | --- | --- |
| `< X nM` (upper bound on Ki) | `pKi > 9 − log10(X)` → interval **lower** bound | `lo >= θ` | **active** |
| `> X nM` (lower bound on Ki) | `pKi < 9 − log10(X)` → interval **upper** bound | `hi < θ`, **or** `hi == θ` with the endpoint **excluded** | **inactive** |
| either, otherwise | interval straddles θ | — | **ambiguous**, never a label |

**Boundary handling, explicitly.** Our rule is `pKi >= θ` is active, so:

- an **inclusive** lower bound exactly at θ is decisively **active** — the
  interval admits θ, and θ is active. Inclusivity is in fact irrelevant on this
  side: `pKi > θ` implies `pKi >= θ`, so `lo >= θ` decides either way.
- an **inclusive** upper bound exactly at θ **cannot decide**. It admits θ
  itself, which is active, while the rest of the interval is inactive. It is
  ambiguous.
- an **exclusive** upper bound exactly at θ is decisively **inactive** — the
  interval is entirely below θ.

Relations are preserved as bounds throughout; a censored record is never
flattened to a point value. Newly decisive evidence — in **either** direction —
is eligible and reported as its own stratum (§4).

**Discordance, and why it is not a label question.** M4 flags a pair whose exact
observations span more than `DEFAULT_DISCORDANCE_PKI = 1.0` log unit as
`discordant`, and withholds it from validation and test while leaving it
available for training. The harness carries that rule across by **reusing M4's
own `exclusion_reason` and precedence**, not by reimplementing them.

The distinction this forces is between **label/status** and **scoring
eligibility**:

* a discordant pair **has** a label and an `ok` status — its exact median is a
  perfectly well-defined number;
* what it lacks is the standing to be scored, because replicate values four logs
  apart cannot arbitrate a ranking.

So the two are reported separately, and the statistics that justify the exclusion
(n, median, min, max, spread) are **retained for audit** rather than discarded
with the pair. Contradiction outranks discordance in the reason, as in M4:
contradictory evidence leaves no label at all, whereas discordant evidence has
one that simply cannot be trusted to rank.

**Recurrence.** Reported for every evaluation pair — whether the pair, the
compound or the target had any slot in A, with counts. Three strata reported
separately: new pair / new compound on a known target / new target.

### 5.5 Frozen versus exploratory

**Frozen before the evaluation snapshot is read** — digests recorded, no
refitting afterwards:

- architecture and hyperparameters: the M9 dual encoder at `h = 512`, the
  affine-on-cosine head, the contrastive margin, the seed list — *carried over
  unchanged*, not re-swept;
- the curation rules in `configs/curation_v1.yaml` and the endpoint builder
  version;
- the metric set, tie handling, and the primary metric;
- the eligibility and exclusion rules above.

**Exploratory regardless of outcome:**

- anything compared against M8/M9 numbers, because those were produced on a
  corpus whose test partitions we have inspected;
- any pooled figure dominated by recurrent pairs;
- any per-target metric on a target with few eligible new pairs — the minimum
  counts must be pre-declared and reported alongside.

## 6. What would actually be measured

Primary: per-target ranking on the **new-pair stratum only** — recall@k, EF@1%
and @5%, BEDROC(α=20), AUROC, and AUPRC with its positive rate — macro-averaged

## 7. An archived as-of split is **not** automatically confirmatory

This is the part that cannot be engineered around.

**What we have already seen.** We have read the full 202609 corpus; we built and
inspected M8 baselines across the **four scored splits** *including their test
partitions* (`label_reversal-v3` is and remains unscored); we ran M9 on those
same four splits and read those test results; we selected a docking target and
cohort from the same corpus for M10. The M9 contract already records
`comparison_mode: exploratory` and
`confirmatory_evaluation_deferred_to: "M11 true as-of temporal split"` for this
reason.

**Why that contaminates an archived split drawn from inside that timeline.**

The argument needs an overlap premise, and that premise is **unverified**:

> *Assumed, not established:* a 2026 snapshot carries most of the content of
> earlier snapshots, so archived deposits from 2024 and 2025 overlap heavily with
> the 202609 corpus we have read.

We cannot currently assert **containment** — that 202609 holds *every* record of
*every* earlier snapshot. BindingDB withdraws and revises records, so an earlier
deposit may well contain rows absent from 202609; §4 treats removals as a real
class precisely because they occur. Quantifying the overlap requires the diff
this milestone has not yet run, and it is listed as an open question (§9).

The exploratory classification does **not** depend on that premise. It follows
from **prior corpus exposure and inspected results**, which are facts about what
we have read rather than claims about set inclusion: we have read the 202609
corpus and the M8/M9 test-partition results, and an archived split drawn from
within that timeline would draw its evaluation labels largely — on the assumption
above, and at minimum substantially — from data we have already seen. Even if the
overlap turned out to be partial, the selection and curation decisions below were
still made by someone who had seen it. Three concrete channels:

1. **Analyst knowledge.** Curation thresholds, the pooling decision, scope
   filters and the discordance cutoff were settled while 202609 was visible. They
   are frozen in config, which prevents *further* tuning — it does not undo the
   fact that they were chosen by someone who had seen the outcome distribution
   the evaluation will draw from.
2. **Model selection.** `h = 512` and the rest were chosen on 202609 validation
   and then scored on 202609 test, which we read. Carrying that model into an
   as-of split reuses a selection informed by the very labels the split will
   test.
3. **Overlap.** On the entry-date figures of §4.2 the genuinely new slice of a
   nearby release looks small, so a pooled result would be dominated by pairs we
   have already inspected. The size of that effect is **provisional** until a
   real two-snapshot diff measures it.

Freezing, digests, partition-scoped endpoints and train-only transforms all
remain necessary — they remove *measurement-level* leakage and make the
experiment auditable and reproducible. **They do not convert it into a
confirmatory test**, because the thing they cannot remove is that we have read
the corpus the labels come from. That holds whatever the measured overlap turns
out to be.

**What would be genuinely confirmatory.** Either:

- **(A) an uninspected future release.** Freeze the complete specification now —
  model, curation, code, metrics, eligibility, minimum counts, the decision rule
  — with digests published and a dated attestation. Then evaluate **once**, on a
  release cut *after* that freeze, without inspecting it first. This is
  achievable: BindingDB cuts quarterly, and the accrual figures say the gap needs
  to be quarters-to-years, so the freeze-and-wait period is the same order as the
  waiting we would do anyway. Its integrity rests entirely on the freeze being
  auditable and the evaluation being run once — a second look makes it
  exploratory again.
- **(B) independently withheld labels.** A third party holds a label set we never
  see. Not available to us here, and worth stating plainly rather than leaving as
  an implied option.

Anything else — including a carefully constructed archive-to-archive split — is
at best a **better-controlled exploratory evaluation**, and should carry that
label in the leaderboard exactly as `temporal_proxy` carries its own.

The standing banners are unaffected and remain: the
`provisional_pooled_for_exploratory_benchmark` status, `label_reversal-v3`
unscored, `temporal_proxy-v4` `train_only` with partition-specific endpoints.

## 7a. The rules checked against worked examples

> **Vocabulary correction (M11e closeout).** Four places in this document called
> the exact-versus-bound contradiction `unresolved_heterogeneity`, which is the
> word the project plan's §1 used for the `pair_label` status. M4 implemented it
> as **`exact_bound_conflict`**, and `unresolved_heterogeneity` is not a status any
> code produces. The behaviour was never in question — such a pair is screened out
> of the primary branch either way — but the name is now the implemented one
> throughout. All eight examples below were reviewed against the implementation
> in `reports/m11e_ki_aggregation.md` §11; the decisions matched, and this name was
> the only discrepancy found.


Eight cases. The first six were traced by hand; (g) and (h) were found by
*implementing* the semantics and are now regression tests in
`tests/test_m11_evaluation.py`. Each states what training gets, what evaluation
gets, and what the audit records — because the defect in the
previous draft was that these three were conflated, and (e) and (f) additionally
separate the three readings of "what B says" from §5.2a.

Notation: slot `S = (inchikey, seq_sha256, pub_ref, pH, T, source)`;
value `V = (type, relation, value)`.

### (a) An unchanged measurement, present in both snapshots

```
A: S → {V1} × 1        B: S → {V1} × 1
```

Counts equal at `(S, V1)` → **unchanged**.

| | |
| --- | --- |
| Training | **included.** It is eligible evidence in A. Its survival into B is irrelevant. |
| Evaluation | **not included** — B adds nothing at this slot. |
| Audit | nothing to record. |

This is the case the previous draft got wrong: "in A only → train" would have
*excluded* it, and since nearly every measurement is unchanged, training would
have collapsed to the handful of rows that happened to disappear.

### (b) A later correction

```
A: S → {(KI, '=', '12 nM')} × 1
B: S → {(KI, '=', '21 nM')} × 1     reactant_set_id identical
```

The two values differ, so there is no `(S, V)` match. Step 3 of §3.2 yields one
unmatched **removal** of `(KI,=,12)` and one unmatched **addition** of
`(KI,=,21)` at the same slot. §3.3 finds exactly one of each at that slot and an
identical `reactant_set_id`, so it asserts a **corrected measurement** — a
*provisional* link, because surrogate stability is unestablished.

| | |
| --- | --- |
| Training | **includes the A value, 12 nM, unchanged.** This is the whole point: an analyst at `T_train` had 12 nM. Substituting 21 nM would import the future; dropping the row would make history depend on it. |
| Evaluation | **excluded.** There is no stable label to score — the measurement is the thing that moved. |
| Audit | slot, both values, the link evidence, and the flag that the model was trained on a figure later revised. |

Had the `reactant_set_id` differed, the same rows would instead be reported as an
**unresolved removal** plus an **unresolved addition**, and no correction would be
claimed. Training treatment is identical either way.

### (c) A withdrawal

```
A: S → {V1} × 1        B: S → {} (slot absent)
```

**Removed slot**; with no addition at that slot there is nothing to link, so it is
a withdrawal, not a correction.

| | |
| --- | --- |
| Training | **includes V1.** A withdrawal discovered in B must not edit the historical population. |
| Evaluation | **not included** — B offers no observation here. |
| Audit | recorded as a withdrawal, counted per target and per curation source. |

If withdrawals cluster on a target that also carries training labels, that is a
reportable limitation of the training evidence — reported, not repaired.

### (d) Repeated identical rows

```
A: S → {V1} × 2        B: S → {V1} × 3
```

Count 2 → 3 at `(S, V1)`: two **unchanged** pairings and one **addition**.

| | |
| --- | --- |
| Training | both A rows included, as two indistinguishable observations. |
| Evaluation | the one added observation is eligible new evidence at a recurrent pair — so it lands in the **recurrent** stratum, not the new-pair stratum. |
| Audit | the count change, with **no claim** about what the repetition means. |

Per §3.4 we do not assert these are duplicate experiments. If they are replicates
the added row is genuine new evidence; if it is re-ingestion it is not; the files
do not distinguish the two, and the aggregation already summarises a slot by its
observations rather than weighting rows by provenance.

### (e) A clean training pair that becomes contradictory later

```
A: pair P → exact median pKi 8.0, no censored evidence   → label active, clean
B: pair P → plus '> 10000 nM' (pKi < 5) from a new source
            → exact value now outside the censored interval
```

Traced through the §5.2a separation, which is what the earlier draft lacked:

| | |
| --- | --- |
| **(i) increment label** | the added observation is `> 10000 nM` → `hi = 5.0 < θ = 6.0` → decisively **inactive**. So the increment *does* yield a label. |
| **(ii) full-B status** | A's exact 8.0 lies outside the increment's interval → `exact_bound_conflict`. |
| **(iii) screen** | full-B status is `exact_bound_conflict`, which is in `SCREENED_STATUSES`, so the primary protocol **drops P**. |

| | |
| --- | --- |
| Training | **P stays, with its A label, active.** Unchanged under both the screened and unscreened branch. Excluding P because B contradicts it would make the historical training set a function of the future. |
| Evaluation, **primary (screened)** | **excluded** |
| Evaluation, **sensitivity (unscreened)** | **included as inactive**, in the **recurrent** stratum — P had slots in A |
| Audit | clean-in-A → contradictory-in-B, both evidence sets, the new source, and which branch included it |

The earlier draft asserted only the "excluded" line and justified it by "B's
eligibility rules", which read like label semantics and was not the same rule
§5.2 stated. Both numbers are now reported, and the choice between them is
pre-registered rather than made on sight of the results.

### (f) A clean active pair in A receiving one decisive *inactive* bound in B

The case that forced §5.2a to be written down. Distinguished from (e) only by
there being no exact/censored *contradiction* to detect — here A's evidence is
itself censored, so there is no exact value to fall outside anything.

```
A: pair Q → '< 1 nM'  → pKi > 9   → lo = 9.0 >= θ=6.0 → decisively ACTIVE, clean
B: adds     '> 10000 nM' → pKi < 5 → hi = 5.0
```

| | |
| --- | --- |
| **(i) increment label** | the added bound alone gives `hi = 5.0 < θ` → decisively **inactive** |
| **(ii) full-B status** | intersecting `pKi > 9` with `pKi < 5` gives an **empty interval** → `empty_intersection`, not merely ambiguous |
| **(iii) screen** | an empty intersection is a contradiction, so the primary protocol **drops Q** |

| | |
| --- | --- |
| Training | **Q stays, labelled active** from A's decisive lower bound. Invariant across both branches. |
| Evaluation, primary | **excluded** — the two bounds cannot both hold |
| Evaluation, sensitivity | **included as inactive**, recurrent stratum |
| Audit | the empty intersection, both bounds, and that the training label came from the `< 1 nM` branch |

This example also exercises the censoring correction of §5.4: A's label here is
**active** and it comes from a *censored* record, which the earlier draft's
"decisive censored records are negatives" would have got backwards.

### (g) A withdrawal that makes B *cleaner* than A

The fixture that exposed the full-B defect. A holds a decisive **inactive** bound;
B **removes** it and adds an exact **active** measurement.

```
A: {'> 10000 nM'}                      -> hi = 5.0 < theta -> INACTIVE, clean
B: {'= 10 nM'}                         -> pKi 8.0          -> ACTIVE,   clean
   added   = {'= 10 nM'}
   removed = {'> 10000 nM'}
```

| | |
| --- | --- |
| **(i) increment label** | the added exact alone → **active** |
| **(ii) full-B status** | B holds one exact value → `ok`, **active**. Nothing contradicts anything. |
| **(iii) screen** | nothing to screen |

| | |
| --- | --- |
| Training | **retains A's inactive evidence and A's `inactive` label.** The bound was real at `T_train`, and B withdrawing it later cannot reach back. |
| Evaluation, primary | **included, as active** |
| Audit | the withdrawal, and the fact that training was fitted on evidence B has since retracted |

**What the old computation did.** `A + additions` = `{'> 10000 nM', '= 10 nM'}`,
whose exact value sits outside the bound → `exact_bound_conflict` → screened out.
A pair B is entirely comfortable with was rejected on a row B does not have. Note
the direction of the error: it **suppressed** a usable evaluation pair rather than
admitting a bad one, so it would have shrunk the evaluation set silently.

Contrast with the same pair when nothing is withdrawn: if B held *both* rows the
contradiction would be genuine and the screen correct. The two cases differ only
in `removed`, which is why `removed` has to exist in the model.

### (h) Discordant replicates: a label without the standing to be scored

Two exact values added for one pair, four logs apart.

```
B adds: {'= 1 nM', '= 10000 nM'}   -> pKi 9.0 and pKi 5.0, spread 4.00
```

| | |
| --- | --- |
| **label / status** | median pKi 7.0 → `ok`, **active**. A label genuinely exists. |
| **scoring eligibility** | `discordant` — spread 4.00 > `DEFAULT_DISCORDANCE_PKI = 1.0` |

| | |
| --- | --- |
| Evaluation, primary | **excluded** |
| Evaluation, sensitivity | **excluded** — this is not a consistency-screen matter, so lifting the screen does not admit it |
| Training | unaffected; M4 leaves discordant pairs available for training |
| Audit | n = 2, median 7.0, min 5.0, max 9.0, **spread 4.00** — retained, because the spread *is* the finding |

This is why label/status and eligibility are separate fields rather than one
verdict. Collapsing them would force a choice between discarding a well-defined
median and scoring a ranking on evidence that disagrees with itself by four orders
of magnitude. Note also that a discordant pair is excluded from **both** branches,
unlike a screened pair which the sensitivity branch admits — the two exclusions
answer different questions and are reported under different keys.

### What the examples establish

- Training is reproducible from A's digest alone. In all eight cases, nothing read
  from B changed it — not an addition, not a correction, not a withdrawal — and it
  is identical under the screened and unscreened branches. That is the checkable
  form of the as-of claim.
- (g) shows the screen must read **actual B**. Reconstructing B as `A + additions`
  is wrong exactly when B removes something, and it fails in the direction of
  silently shrinking the evaluation set.
- (h) shows why **label/status and scoring eligibility are separate**. A
  discordant pair has a label and is still not scoreable, and it is excluded from
  both branches rather than one.
- Corrections, withdrawals and newly-contradictory pairs affect **evaluation
  eligibility and the audit record only**.
- The slot/value separation makes (b) expressible at all: a single fingerprint
  containing the value could not have represented a value change.
- (d) shows why counted multisets are needed rather than sets, and why the
  interpretation of repetition stays open.
- (e) and (f) show that "what B says" needs the three-way split of §5.2a. Both
  yield an increment label *and* a full-B contradiction, so a protocol that did
  not separate them would silently report whichever it happened to compute.
- (f) exercises an **active** label drawn from censored evidence, the branch the
  earlier censoring text omitted.

| Question | Answer |
| --- | --- |
| Can we get an earlier snapshot from bindingdb.org? | **No** — past monthly releases 404, including our own 202609 |

| Would an archive-to-archive split be confirmatory? | **No** — prior corpus exposure and inspected results, independent of how large the overlap proves to be |
| Is a confirmatory evaluation possible at all? | **Yes**, by freezing now and evaluating once on a later, uninspected release |

## 9. Unresolved questions

1. **Which quarterly deposits exist**, with dates, DOIs, file names, sizes and
   per-deposit licence metadata. Blocks snapshot selection entirely.
2. **Is `reactant_set_id` stable across releases?** Unknown, and §3.3 depends on
   it: every correction link is provisional until it is settled. The
   content-vs-surrogate disagreement count is the experiment that answers it, and
   it needs two snapshots.
2b. **How much do archived deposits actually overlap?** The §7 premise is
   unverified. The diff measures it, and it also measures the removal rate —
   which decides whether "containment" was ever a safe assumption.
3. **Licence terms for the specific deposits** — CC BY 3.0 versus 4.0 for
   BindingDB-curated rows, and the share-alike obligation on ChEMBL-derived rows.
4. **Does an archival deposit carry the three auxiliary files** (`rsid_eaids`,
   `Assays`, target FASTA)? Assay context and the three-way join depend on them;
   without them an archived snapshot cannot reproduce our curation.
5. **How BindingDB records revisions** — whether a corrected measurement is
   distinguishable from a new one in the files themselves, or only by diffing
   snapshots.
6. **What the minimum eligible new-pair count should be** for a per-target
   ranking metric to mean anything, declared before snapshots are chosen — and
   measured from a real diff rather than from entry-date counts.
7. **What repeated identical rows represent** — replicate experiments, double
   ingestion, or uncaptured condition differences (§3.4). The files do not say.

### `diff_snapshots` does not fit in memory as written

It takes `earlier` and `later` as in-memory `list[dict]`. Measured on this
machine, loading 100,000 exported rows and converting them to `Observation`
objects costs **2,492 bytes per row dict and a further 1,473 bytes per
observation**. Over both snapshots' 6,370,799 observations:

| | Measured cost |
| --- | ---: |
| Row dicts alone | **15.9 GB** |
| Row dicts + `Observation` objects | **25.3 GB** |
| `_group`'s `Slot`/`Value` index | not measured; strictly additional |

Physical memory is **16 GiB** (`hw.memsize`). So a single full-corpus
`diff_snapshots` call cannot complete, and would fail only *after* loading both
sides — the worst point at which to find out. The per-row costs above are
measurements taken on the real exports, not extrapolations from a published row
count; the wall-clock cost of that load was **not** measured and is not claimed.

### Slot-hash sharding, and why it is sound rather than merely convenient

Every decision `diff_snapshots` makes is scoped to one slot. `_group` keys on
`Slot`; the counted multiset pairing of §3.2 compares value multiplicities within
a slot; `_link` proposes correction candidates from the surplus removals and
additions *at that slot*; `new_slots` and `removed_slots` are per-slot by
definition. No rule reads across slots.

And every `DiffReport` field composes: `unchanged`, `additions`, `removals` and
both `unresolved_*` are `Counter`s, which add; `new_slots`, `removed_slots` and
`ambiguous_slots` are sets, which union; `correction_candidates`,
`identifier_conflicts` and the four `*_rows` lists concatenate.

So: stream both exports, assign each row to shard `H(slot) mod K`, diff each
shard pair independently, and merge. Correctness depends on one invariant —
**every row sharing a slot lands in the same shard** — which hashing the
serialised slot guarantees. Determinism depends on merging shards in a fixed
order and re-sorting the detail lists, which `_rows` already does internally.

This is a decomposition of the existing matcher, not a second implementation of
it. The per-shard call is the same tested function.

### The original proposal

Narrower than M11d on purpose. M11d matched all four measurement types because a

2. **Aggregate to pairs through the existing bridge and endpoint rules**, so
   censoring, interval intersection, discordance and the threshold boundary
   behave exactly as M4 defines them rather than being restated. Aggregation is
   per compound–target pair and therefore runs **across** slots and across

3. **Build the three representations** of §5.2a0 — `in_a`, the complete actual

4. **Then declare the minimum eligible new-pair count** (item 8), sized against

5. Report with the provisional-pooling banner and the exploratory label intact.

**The number that decides whether this snapshot pair is worth evaluating at all**

it is unknown in a way that matching could not have resolved: eligibility depends
on how the additions aggregate per pair against prior evidence, and M11d's
slot-scoped output deliberately stops short of that.

One caveat to carry forward. **28,129** of the cross-slot candidates gained a
publication reference, 102 changed from one attribution to another, and **none

in ambiguous ones. Whether it inflates the eligible KI increment, and by how much,
is a question for the aggregation step: a re-attributed row is a genuine addition
*at its slot*, so the slot-level diff cannot net it out, and pairs are what
eligibility is computed over.
